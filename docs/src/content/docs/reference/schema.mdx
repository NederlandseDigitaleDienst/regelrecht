The law format is defined by a JSON Schema. Every rulework in the corpus must conform to this schema.

Everything below the version history is generated from the released schema itself, so this page and the contract cannot disagree. Where a field has a concept page, the table links to it.

This page owns the field-level detail, down to which operands each operation takes. How a rulework is put together, and why, is walked through on one real article in [Law Format](/concepts/law-format).

## Current Version

The current schema version is **v0.8.21**.

Schema URLs use immutable git tags to guarantee reproducibility. The format is:

```
https://raw.githubusercontent.com/NederlandseDigitaleDienst/regelrecht/refs/tags/schema-v0.8.21/schema/v0.8.21/schema.json
```

The tag `schema-vX.Y.Z` is created when a schema version is released. Using tags instead of `refs/heads/main` ensures that the schema a version of a rulework references can never change underneath it. See [RFC-013](/rfcs/rfc-013) for the rationale.

| v0.8.21 | `FOREACH` takes `combine: DISTINCT`: the unique results as an array, in the order each first occurs. Two results are the same when `EQUALS` says so, a number, amount, string, date or boolean by value and a row or list field by field; `null` stays once, and an empty collection gives an empty array. One value of several equal ones is `ONLY` over the result of `DISTINCT`, and `ONLY` stays strict. A file on v0.8.20 or earlier that uses `DISTINCT` is refused | [RFC-016](/rfcs/rfc-016) |
| v0.8.20 | A property of the state of a projection may be an `array` with its `columns`, each a name and a scalar type (boolean, number, string, amount or date), so it holds a table; in the state an `array` always declares its columns. It starts as an empty list and is never null. A step replaces the array whole with a bare reference, such as `$record.<field>` for an array of rows a fact holds; a row lacking a column holds null there, and a row with a column the array does not declare, or with a value that is not of its column's type, fails the step. A parameter of type `array` may declare its `columns` too (`arrayColumn`), and the loader holds an array in the state to the columns of the fact field or state property it is filled from, where that source declares them. A read model reads the array as a field of the row of its aggregate and iterates over it with a nested `FOREACH`. A property of the state may also declare `nullable: true`: a boolean, number or amount then starts as null and a step may set it to null, while a string or a date may hold null as before and an array never does. The loader refuses a step that fills a property that is not nullable from a source that may be null. A file on v0.8.19 or earlier keeps loading as it did, and one that has an array with columns or `nullable` in its state is refused | none yet, an experiment |
| v0.8.19 | Each article of a `REDUCTIE` with a `machine_readable` takes one of two forms: an aggregate, a `projection` with `per` and no `execution`, or a read model, an `execution` that reads aggregates (`source.projections`). One file may hold both; an article that is neither, or both, is refused. `source.projections` names the article of the aggregate, `<regulation>#<article>`, also in the reading file itself; the reduction alone is refused, and so is a reference to an article that does not exist or plays no aggregate. An article of a reduction that only calls other rulework reads no chronicle and is refused; such a rule belongs in policy. A file on v0.8.18 or earlier keeps loading as it did, `source.facts`, a reference to the reduction alone and a reduction without aggregates included, so such a file is not valid under v0.8.19 unchanged | none yet, an experiment |
| v0.8.18 | The third segment of `projection.per` and of `steps[].record` may be the name of a fact the article requires, in lower case: `<regulation>#<article>#<fact>` addresses the executograms of that fact alone, and `$record` in such a step reads the fields of that fact. The loader refuses a fact name the article does not require, and refuses it in a file on v0.8.17 or earlier. From v0.8.18 the loader also holds `per` to the article it names, as it holds a step. `per` names a kind the article gives or a fact it requires. Without either, the article gives one kind of record and requires at most one fact. A file that declares v0.8.17 loads as before; moved to v0.8.18, its `per` must meet these rules | none yet, an experiment |
| v0.8.17 | A projection plays one aggregate per record of a kind: `projection.per` names the article the root rests on (`<regulation>#<article>`, with `#<KIND>` where the article gives more than one kind). An aggregate is the root and the records that refer to it through `refers_to`, transitively; another record of the root's kind that refers in is an aggregate of its own and counts there for its effects only. Such a projection answers no question of its own and has no `execution`. Another reduction reads it with `source.projections`, by the `$id` of that reduction: one row per root the chronicle holds on the calculation date, the last state of its aggregate with the root's `id`, and with `where` only the roots that hold the value of a parameter under a name. A reduction reads no decisions any more (`source.decisions`): a row about a decision comes from an aggregate. `key` is gone, and a step passes no parameter of the question (`$<name>`): its parameters are `$record.<field>` and `$state.<property>`, so a fold depends on the chronicle alone. A step of a projection with `per` reads `$record.refers_to`, the id of the record its record refers to, or null. `refers_to` names, on every record, the record this record is about, so any fact may refer to an earlier record of the chronicle, with or without effects, and a decision taken on no submission refers to the decision it affects. A decision revokes only a record it is about: one its `refers_to` reaches, directly or through the records it refers to in turn; the cell and the engine refuse another. A file on v0.8.16 or earlier keeps loading as it did, `key`, question parameters and `source.decisions` included, so such a file that uses one of them is not valid under v0.8.17 unchanged | none yet, an experiment |
| v0.8.16 | A step of a projection is held to three stricter rules: the article it is on must give a record, `$record` reads only the fields of the kind of record the step is about, and the step passes every required parameter that the output it takes reads, directly or through another output of its article. The loader checks the steps when the reduction loads, against the newest version it holds of each law they name, and the engine again when it plays the projection. A reduction on v0.8.15 or earlier still loads under the old rules and is checked only when it plays, so a v0.8.15 file that breaks one of the new rules is not valid under v0.8.16 unchanged. One rule is looser in every version: a step may take an output of an article that has an `input` or an open term, as long as that output does not read them, directly or through another output of its article | none yet, an experiment |
| v0.8.15 | A fact an article requires may have `effects`, as a decision has them: `requires[].effects` with `revokes: refers_to`, so a fact revokes the record it refers to, and optionally `when`, a boolean parameter the fact holds. The receipt of a copy of a ruling that annuls a decision (Awb 8:72 lid 1, 8:79) revokes the decision it refers to this way; a fact with effects may also refer to another earlier record of the chronicle. An effect of a decision may name any earlier record, a fact too. `revokes` means the record does not count, from the start (ex tunc). The annotation schema (`annotation-schema.json`) versions independently of the law schema: it is republished only when it changes. It was introduced at `schema/v0.5.2/` and last republished at `schema/v0.5.3/`, which is the version the validators embed.

## About this reference

The sections above are generated from the released schema at build time, so this page cannot describe a schema other than the released one. That guard is about the version, not the wording: a description that has fallen behind what the engine does is still a description this page will render faithfully. [RFC-040](/rfcs/rfc-040) sets out why the schema carries its own documentation and how the generated page is held to it.

The version history is not generated: it records what a version introduced and why, which is a judgement no schema can state about itself.

The schema is JSON Schema draft-07. It uses none of the constructs that changed in later drafts, so it would migrate to 2020-12 mechanically; the one keyword that would be worth having is `deprecated`, which arrived in 2019-09. That is a decision for its own RFC, since the schema is a contract other engines read ([RFC-013](/rfcs/rfc-013)) and draft-07 is the most widely implemented dialect.

One consequence of draft-07 shows up here. Where a field is a `$ref` to another definition, a `description` written next to that `$ref` is formally ignored: draft-07 says a `$ref` replaces its siblings. This page reads those descriptions anyway, falling back to the target's, so nothing is lost in what you see. An editor that follows the specification strictly will not show them.

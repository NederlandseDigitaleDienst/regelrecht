These notes are for someone who writes or maintains a rulework and wants to move its `$schema` to a newer version. Each note says what the version changes for that person, whether a version of a rulework that validated under the previous schema still validates, what to edit when it does not, and how the new construct looks in use.

The [version history](/reference/schema#version-history) on the schema reference stays the record of which version introduced which construct, and it is the table RFCs cite. Each row from v0.8.0 on links to its note here. The note does not repeat the row: it adds what the row leaves out, which is what an author has to do.

Where a version removes a construct, leaving the `$schema` of a rulework on the older version keeps it valid against that schema, but it does not keep it running. The engine in this repository runs every version on one code path and refuses a removed construct when it loads the rulework, naming the replacement where there is one. So where a note says a version is not additive, the rulework has to be edited before the engine will run it, whatever its `$schema` says. The one change neither the schema nor the engine catches at load is the rename in [v0.8.12](#v0812).

The notes cover v0.8.0 to v0.8.14. Versions before v0.8.0 have no note; for those, the version history is all there is.

## Where the examples come from

No example on this page is typed in. Each one is a marked excerpt of a fixture in `packages/engine/tests/conformance/`, read when the site is built. `just conformance` checks every fixture in CI: a fixture under `valid/` must pass the schema and survive a round trip through the Rust model without losing a field, and a fixture under `invalid/` must be refused by the schema version its `$schema` names. An example here therefore cannot show something the schema does not accept, and an example of a shape to change cannot show something the schema still accepts.

The fixtures under `valid/` that these notes draw on currently declare the newest schema, so a positive example shows the construct as the current schema accepts it. That can be a little later than the version the note is about, and where a later version changed the construct, the note says so.

## v0.8.14

Two additions, both experimental and without an RFC so far. A decision can say what it does with another decision, and a reduction can play its cell's chronicle forward and answer from the state it ends in.

Additive: a version valid under v0.8.13 is valid under v0.8.14 unchanged.

A decision in the list form of `produces` names its `effects`. With `revokes`, the decision revokes the decision held by the parameter it names, as a decision on an objection revokes the contested one (Awb 7:11 lid 2). `when` makes the effect conditional on a boolean output of the same decision, so the objection revokes only when it is well-founded:

<FixtureExcerpt fixture="valid/v0_8_14_decision_effects.yaml" region="in-place" />

A `REDUCTIE` may have a `projection`. Its `state` lists named properties with a type, and each starts at the value of that type: false, 0, or null for a string or a date. `steps` has one entry per article a record rests on. A step takes outputs of a law the way an article does, with an `input` whose `source` is `regulation`, and its `actions` give properties their values, each as a bare reference to an input, a field of the record (`$record.<field>`) or the state before it (`$state.<property>`). The step computes nothing itself; what a record does stays in the law it calls. `record` may name the kind of record in a third segment, such as `#BESCHIKKING`, and has to when the article gives more than one kind. With `key`, only the records of the person asked about are played. The reduction's `execution` answers from the last state.

Which records count follows from the effects: a record counts unless a later record that itself counts revokes it, and only the records that count change the state.

A step may also pass a parameter of the question to the law it calls, such as the day the question is about. The answer then depends on that parameter, as it does on the key. This step leaves out the third segment, which is allowed because the article gives one kind of record:

The engine plays a projection only where a chronicle is played: when a cell gives the reduction's answer to a policy through `source.reduction`, or through `evaluate_projection` in the Rust engine. Asked for directly, from another rulework or at a stage, it refuses the article.

## v0.8.13

`combine` is gone from open terms (where v0.8.8 put it) and from a `source` beside `reduction` (where v0.8.9 put it). There it told the engine how to merge the answers of several cells. The `combine` of a `FOREACH` is a different field and stays. The engine now asks one cell and merges nothing; when the call that a term names has more than one cell, the input fails at run time.

A version that uses `combine` in neither place validates under v0.8.13 unchanged. One that does no longer validates: remove the field. A term may still list several competent authorities, and the schema accepts that; what fails, at run time, is a call that holds a cell for more than one of them. How one question would reach several cells of a category is an [open question](/concepts/chronolexography/open-questions), so there is no replacement construct yet.

## v0.8.12

Two changes, both about reductions. The article a decision value was taken under is now called `basis`, where it was `grondslag`: in the decision value, in the rows of `source.decisions` and `source.facts`, and in `$besluit.basis`. And a `REDUCTIE` no longer names a `competent_authority`; the directory it sits in says whose it is.

Not additive. A reduction with a root `competent_authority` is refused: delete the field and put the version under its cell, in `corpus/cells/<cell>/reductions/`, or in `corpus/cells/reductions/` if it belongs to no cell. The rename is one the schema cannot see, because `basis` is the name of a value at run time and not a key in the document. An action that reads `$besluit.grondslag` still validates and still loads, but the decision value it reads has no field of that name any more. Search for `grondslag` and replace it.

## v0.8.11

`source.decisions` may take the article to search under from a parameter, as a `$`-reference, instead of naming it. That lets one reduction answer for decisions under any article, with the caller saying which. It reads the chronicle of the cell that runs it.

## v0.8.9

A reduction stops filling open terms. It becomes a named answer of its cell, and the policy of the authority that decides (`regulatory_layer: UITVOERINGSBELEID`) binds an open term to that answer, with `implements` and an input whose `source` is `reduction`. The policy names its holder in a root `competent_authority`.

Not additive. A `REDUCTIE` with `implements`, which v0.8.5 allowed, is refused. Remove `implements` from the reduction, let its cell give it as an answer under the name the policy will ask for, and move the `implements` to an article of the policy that takes the answer through `source.reduction`.

## v0.8.8

An open term and a required fact may say who is competent for them, with their own `competent_authority`: one named authority or a list. On the term it names who may answer it, on the fact who establishes it. The article's own `competent_authority` still names who decides, which is a different question.

Additive: a version valid under v0.8.7 is valid under v0.8.8 unchanged.

## v0.8.7

An article can say that it requires a fact to exist: a `requires` entry with `fact`, the article's `parameters` the fact holds, and a `description`. A reduction reads the recorded instances of that fact through `source.facts`, named `<regulation>#<article>#<fact>`, which replaces the `source.executograms` of v0.8.6.

Not additive. A reduction that read a stream with `source.executograms` is refused. Declare the fact on the article that requires it, then name it in `source.facts`.

## v0.8.4

An input can call the decision of an article with `source.article`, named as `<regulation>#<article>` or by a `$`-reference to a value that holds one. Without `output` the input is a whole decision value, with the field type `decision`; with `output` it is one output of that decision. `source.parameters_from` merges objects into the parameters of the call, and `derived` on a decision lists outputs computed for it that the decision value leaves out.

## v0.8.2

A new layer, `regulatory_layer: REDUCTIE`. A reduction is not a regulation: it is a cell's reading of its own chronicle, and it is kept with the cell rather than in the corpus of regulations. It reads the decisions taken under an article with `source.decisions`, which gives a list with one row per decision. Only a reduction may read it, and a reduction does not act on law: no `implements`, `hooks`, `overrides`, `execution.produces` or `open_terms`.

Additive: a version valid under v0.8.1 is valid under v0.8.2 unchanged.

## v0.8.1

`execution.produces` may be a list instead of one object, for an article that produces more than one thing, such as an application and the decision on it. Each item has a `type`, a kind of submission or a legal character, and says which of the article's parameters it contains and which outputs it yields. A submission names the article whose decision it asks for with `requests`.

Additive: the object form is unchanged, so a version valid under v0.8.0 is valid under v0.8.1 unchanged.

## v0.8.0

An article can establish a submission (`produces.submission`, with `kind: AANVRAAG`) and state the moment that counts for it in law (`produces.moment`), with the provision behind that moment as a `legal_basis`. ## Adding a release note

A pull request that adds a schema version adds its note to this page, at the top, under a heading that is the version number alone (`## v0.8.14`). The heading is the anchor the version history links to, so keep anything else out of it. In the same pull request:

1. Link the version cell of the new row in the [version history](/reference/schema#version-history) to the note, as the rows below it do.
2. Say whether a version valid under the previous schema stays valid, and when it does not, what to edit.
3. Take the example from a conformance fixture. Put `# release-note-begin: <region>` and `# release-note-end: <region>` comments around the lines to show, in a fixture under `valid/` for the new construct or under `invalid/` for a shape the version refuses, and render them with `<FixtureExcerpt fixture="valid/<file>.yaml" region="<region>" />`. If no fixture fits, add one first; [Conformance](/reference/conformance#schema-to-law-model-conformance) and the README next to the fixtures describe how.

`docs/scripts/check-schema-version.mjs` fails CI when a version from v0.8.0 on has no note here, or when its row in the version history does not link to it. A region that is missing or empty fails the site build.

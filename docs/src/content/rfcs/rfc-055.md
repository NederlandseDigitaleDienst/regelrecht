## Context

Every input, output and parameter in a rulework declares a type (`boolean`,
`number`, `amount`, `string`, `date`, `array`, `object` or `decision`), and an
`amount` or `number` may carry a unit (RFC-023). Nothing in the law format says
what an operation does with those types. The engine decides, one function at a
time, and RFC-037's checker rejects only some combinations, only where it knows
the types. The result is behavior no author would predict from the YAML:

- `AND`, `OR`, `NOT`, an `IF` condition and a `FOREACH` filter accept any value
  and treat `0`, `""` and empty lists and records as false, everything else as
  true.
- `ADD` of a date and a string concatenates them as text, because a date is a
  string at run time.
- `DATE_ADD` and `DATE` drop the fraction of a number: `months: 1.5` adds one
  month.
- `EQUALS` of two different types is `false`, except a date string against
  `$referencedate`, which is compared as a date.
- `IN` does not compare the way `EQUALS` does: `IN "2025-01-01"
  [$referencedate]` is `false` where `EQUALS` on the same pair is `true`, and
  a `value` that is not a list is treated as a list of one.
- `DATE_PART` and `START_OF` turn an unknown or absent date into a type error,
  where every other operation passes the unknown on or reports the absence
  (RFC-036).
- `eurocent × percentage` is accepted as `eurocent`, a hundred times the
  amount the law means unless the author also divides by 100.
- `DIVIDE` rounds its result to the roughly 28 digits the engine's decimal
  library holds. The law never asked for that rounding, and it shows:
  `FLOOR((1 ÷ 3) × 3)` is `0`, not `1`.

Several of these were deliberate when introduced. The common cause is that
the law format does not define what an operation does with its operands, so
the engine's code is the only definition. Another engine built to the same
format could make different choices and still conform to it.

No existing type system covers money, units, the difference between an absent
and an unknown value, and the `decision` type together; FEEL, Catala and CQL
were surveyed, and Alternatives Considered says why none is adopted.

## Decision

Every operation has a closed list of signatures: the operand types it accepts
and the type it returns. Operands that match no signature are an error, found
at load time where the checker knows the types and at run time where the value
shows them (see Errors). Nothing is converted implicitly, except in the five
cases listed under Types. A combination a law needs that the table lacks is
added as a new row.

### Types

The signatures use the schema's types. Where a row says `number`, an
`amount` is accepted too; which combinations of amounts and numbers are valid
is in Amounts and units.

- **Whole number.** Where a signature asks for a whole number, `2` and `2.0`
  qualify and `2.5` is an error, never truncated.
- **Equality of numbers.** `42` equals `42.0`. Inside an `array` or `object`
  the two are an error rather than equal, because a stored value is compared
  as written.

The five conversions the format does make:

1. A string literal in the form `YYYY-MM-DD` is a `date` where a signature
   requires one. A value that enters through a field declared `date` is parsed
   as a date when it enters. A string computed at run time is never read as a
   date.
2. `$referencedate`, an `object` with fields `iso`, `year`, `month` and `day`,
   is accepted wherever a `date` is, and its field `iso` is a `date`. The
   engine supplies both, so their type is known.
3. A value without a declaration (a field of a record, a `FOREACH` element) is
   read as a date where a signature requires one, when it is a string in the
   form `YYYY-MM-DD`; otherwise it is an error. That covers the date operations
   and an ordering or `EQUALS` with a date on the other side, so `AGE` with
   `date_of_birth: $kind.geboortedatum` works. A field declared `string` stays
   a string, and `ADD` never reads a date.
4. A `FOREACH` over a value that is not an array iterates once over that value,
   as RFC-016 and the schema define.
5. A plain number beside a number in unit `u` is read as a number in `u`. A
   plain number beside an `amount` is read as eurocents only in a comparison,
   in `IN`, in the outcomes of an `IF` and where a value meets a declared
   output; in adding and subtracting only the literal `0` is. Amounts and units
   lays this down.

### Absent, unknown and untranslatable

`null` (absent), unknown and untranslatable are not types. Every operation
handles them first, as RFC-031 and RFC-036 lay down: an untranslatable marks
the result untranslatable, an unknown makes the result unknown, and `null` is
an error except where RFC-036 and RFC-037 allow it. `AND`, `OR` and `IN` are
the exception: an operand that settles the answer wins over an untranslatable
and an unknown alike (see their rows). The rows below that accept `null` say
so. `DATE_PART` and `START_OF` are no exception to this.

### Signatures

`T` is any type, the same within a row. `…` means one operand or more. The
date and comparison rows follow FEEL, the rules for money follow Catala, and
the rest follow earlier RFCs of this project.

**Arithmetic**

| Operation | Operands | Result |
|---|---|---|
| `ADD` | `number…` | `number` |
| `ADD` | `string…` | `string` |
| `ADD` | `array…` | `array` |
| `SUBTRACT` | `number…` | `number` |
| `MULTIPLY` | `number…` | `number` |
| `DIVIDE` | `number…` | `number` |
| `MIN`, `MAX` | `number…` | `number` |
| `ROUND`, `CEIL`, `FLOOR` | a `number` and a `precision` | `number` |
| `PERCENTAGE_OF` | a `number` and an `amount` or `number` | the second's type |

- `ADD` of strings or arrays joins them in order.
- `SUBTRACT` and `DIVIDE` take the first operand and subtract or divide by the
  rest. Dividing by zero is an error.
- `ROUND` rounds to the nearest, `CEIL` toward +∞ and `FLOOR` toward −∞
  (RFC-024). A tie in `ROUND` goes away from zero: RFC-024 says half-up and
  leaves a negative tie open, and this RFC settles it, so `-2.5` rounds to
  `-3`. `precision` is the number of decimals to keep: a whole number from −28
  to 28, written in the YAML rather than computed. That is the range the
  released schemas state, and no law needs more. A negative `precision` rounds
  to tens or hundreds, so `-2` rounds an amount to whole euros. See also
  Precision.
- `PERCENTAGE_OF` divides by 100; see Amounts and units.

**Comparison**

| Operation | Operands | Result |
|---|---|---|
| `EQUALS` | `T`, `T` | `boolean` |
| `EQUALS` | `T`, `null` | `boolean` |
| ordering | `number`, `number` | `boolean` |
| ordering | `date`, `date` | `boolean` |

- The orderings are `GREATER_THAN`, `LESS_THAN`, `GREATER_THAN_OR_EQUAL` and
  `LESS_THAN_OR_EQUAL`. An earlier date is less than a later one (RFC-021).
- `EQUALS` compares arrays and objects element by element. `EQUALS` with
  `null` tests whether a value is absent (RFC-036).

**Logic**

| Operation | Operands | Result |
|---|---|---|
| `AND`, `OR` | `boolean…` | `boolean` |
| `NOT` | `boolean` | `boolean` |
| `IF` | `boolean` conditions, `T` outcomes | `T` |

- An unknown or untranslatable condition makes `AND` and `OR` unknown or
  untranslatable, unless another condition settles the answer: `AND` with a
  `false` condition is `false`, `OR` with a `true` condition is `true`
  (RFC-036). When nothing settles it, an untranslatable goes before an unknown.
  An `AND` without conditions is `true`, an `OR` without conditions `false`.
- Conditions are evaluated in the order written, and evaluation stops at the
  first one that settles the answer. The conditions after it are not
  evaluated, so the data they read is not fetched (RFC-043): a rulework
  that puts its cheapest or most decisive condition first reads less about a
  person.
- The outcomes of an `IF` are each `then` and the `default`. Without a
  `default`, an `IF` whose conditions are all false gives `null` (RFC-037). An
  outcome may be `null` when the `IF` gives the value of a nullable output
  (RFC-037, rule N2).
- The `filter` of a `FOREACH` is a `boolean` condition as well.

**Collections**

| Operation | Operands | Result |
|---|---|---|
| `LIST` | any values | `array` |
| `IN` | a `T` and an array of `T` | `boolean` |
| `FOREACH` | an `array` | `array`, or see `combine` |

- `IN` is true when an element `EQUALS` the subject. The array is given either
  as `values` or as `value`, never both. Its elements may include `null`, and
  `IN` with a `null` subject is true when the array holds a `null`. A definite
  match wins over an
  untranslatable or unknown element, as a `true` does in `OR`.
- A `FOREACH` over `null` iterates nothing.

`FOREACH` reduces its results with `combine`:

| `combine` | Elements | Result | No results |
|---|---|---|---|
| `ADD` | `number` | `number` | `0` |
| `AND` | `boolean` | `boolean` | `true` |
| `OR` | `boolean` | `boolean` | `false` |
| `MIN`, `MAX` | `number` | `number` | `null` |
| `ONLY` | `T` | `T` | `null` |

`ONLY` with more than one element is an error.

**Dates**

| Operation | Operands | Result |
|---|---|---|
| `DATE` | three whole numbers | `date` |
| `DATE_ADD` | a `date` and whole numbers | `date` |
| `DATE_DIFF` | two dates and a unit | `number` in that unit |
| `AGE` | two dates | `number` in `years` |
| `DATE_PART` | a `date` and a part | plain `number` |
| `DAY_OF_WEEK` | a `date` | plain `number` |
| `START_OF` | a `date` and a part | `date` |

- `DATE` takes a year, a month and a day; a day that does not exist is an
  error.
- `DATE_ADD` adds `years`, `months`, `weeks` and `days`, largest unit first. A
  day past the end of a month becomes its last day: 31 January plus one month
  is 28 or 29 February.
- `DATE_DIFF` counts complete `days`, `months` or `years`, positive when `to`
  is later than `from`. The result carries the unit it counts in, so
  `DATE_DIFF … in: months` gives a number in `months`. Where `in` is computed
  rather than written in the YAML, the result is a plain number.
- `AGE` counts complete years. A birthday on 29 February falls on 28 February
  in a common year.
- `DATE_PART` reads the `year`, `month` or `day`; `START_OF` goes back to the
  first day of the `year` or `month`; `DAY_OF_WEEK` gives 0 for Monday up to 6
  for Sunday.

**Decisions.** A `decision` (RFC-045) is read through its fields, passed on,
and compared with `EQUALS`. Every other operation on a decision as a whole is an
error.

The engine also accepts `NOT_EQUALS`, `IS_NULL`, `NOT_NULL`, `NOT_IN` and
`SWITCH`, which the schema does not. They take the signatures of `EQUALS`,
`EQUALS … null`, `IN` and `IF`.

### Amounts and units

**An `amount` is money, counted in the minor unit of its currency.** This RFC
knows one currency, the euro, so an amount counts eurocents. It is a type of
its own, not a `number` with a unit, because every field declares a type and a
unit is optional: as a unit, money would be checked only where someone
remembered to write it. An amount the law states in euros is written times 100,
as the corpus already does everywhere. Showing euros is a matter for the
screen: a frontend divides by 100 when it displays an amount, and multiplies by
100 when someone enters one. A data source that delivers euros is converted
when its value enters, never inside a rulework. "Rounded to whole euros" is
`ROUND` with `precision: -2` (RFC-024).

The units `euro` and `eurocent` are removed. Two units for one quantity have
produced wrong answers before: with the Awir in `euro` and the zorgtoeslag in
`eurocent`, one person on one income came out at €827.63 or €1,550.46
depending on which convention won, and nothing warned.

**Units** remain for numbers that are not money. A `number` may declare one in
`type_spec.unit`, on a field or on a definition; a number without one is a
**plain number**: a literal such as `100` or `12`, a count, or a field nobody
annotated. RFC-023's rule stays: a plain number is never refused for its
unit. Money is stricter, because it is a type (below).

| Unit | Measures | Example |
|---|---|---|
| `years`, `months`, `weeks`, `days` | a duration | `6` months |
| `ratio` | a share, where 1 is the whole | `0.05` for 5 percent |
| `percentage` | a share, in hundredths | `5` for 5 percent |

No unit converts into another: `years` and `months` are different units, as
are `ratio` and `percentage`.

**A `ratio` and a `percentage` are two scales for one thing.** A ratio counts
on the scale where 1 is the whole, a percentage in hundredths: 143 percent of
the minimum wage is a ratio of `1.43` or a percentage of `143`. Neither has a
range. Because they are different units, one beside the other is an error,
which is what keeps `0.05` and `5` apart.

A ratio above `10` written in a rulework is probably a percentage: `13.7`
declared as a `ratio` would be 1370 percent. The checker warns about it and
does not refuse the rulework (see Errors). The warning looks only at values
written in the rulework, in a definition or as a literal, and it cannot catch
a small percentage written as a ratio: `1.896` reads as 189.6 percent.

The tables below treat `amount` as one more kind beside the units. "Plain" is
a plain number.

**Adding and subtracting.** `ADD`, `SUBTRACT`, `MIN`, `MAX` and the elements
of a `combine` take operands of one kind:

| Operands | Result |
|---|---|
| `amount` and `amount` | `amount` |
| `amount` and the literal `0` | `amount` |
| `u` and `u` | `u` |
| `u` and plain | `u`; the plain number is read in `u` |
| plain and plain | plain |
| anything else | error |

A plain number is not read as money here, because a count or a rate added to
an amount is a mistake that should not pass. A definition that holds money
declares `type: amount`. The literal `0` is the exception, because zero is
zero in every currency: `MAX [0, $bedrag]` sets a floor at zero, and `SUBTRACT
[0, $bedrag]` negates an amount.

A number with a unit does take a plain number beside it, as RFC-023 lays
down. The Leerplichtwet counts school days by adding weekday numbers, which
are plain, to a difference in `days`, and the result is a number of days. Two
different units stay an error: `days + months`, `ratio + percentage`, and
`amount + days`. Here `u` is any one unit, so `1 − $fractie` is a ratio.

**Comparing and choosing.** The orderings, `EQUALS`, `IN` and the outcomes of
an `IF` follow the rows for adding, with one more: a plain number beside an
`amount` is accepted and read as eurocents. A comparison or `IN` returns a
`boolean`; `GREATER_THAN $inkomen 2500000` with `$inkomen` an amount reads
`2500000` as eurocents, €25,000. An `IF` that gives an amount may write a
literal outcome: `default: 0` is an amount of zero.

**Multiplying.** The operands may come in either order:

| × | `amount` | duration | `ratio` | `percentage` | plain |
|---|---|---|---|---|---|
| **`amount`** | error | `amount` | `amount` | error | `amount` |
| **duration** | `amount` | error | duration | error | duration |
| **`ratio`** | `amount` | duration | `ratio` | `percentage` | plain |
| **`percentage`** | error | error | `percentage` | error | `percentage` |
| **plain** | `amount` | duration | plain | `percentage` | plain |

"Duration" in a result is the unit of the operand: `months × ratio` is
`months`. A ratio scales the other operand, and the result has that operand's
kind: `amount × ratio` is an amount, and half of a plain 10 is a plain 5. Only
`ratio × ratio` is a ratio. An amount times a duration is an amount: a daily
amount times a number of days. One `MULTIPLY` or `DIVIDE` pairs an amount with
at most one duration, so `amount × days × days` is an error in any order, as is
`amount ÷ months ÷ months`.

**A percentage of an amount** is the operation `PERCENTAGE_OF`, not a
multiplication:

```yaml
operation: PERCENTAGE_OF
percentage: $tarief   # 21 for 21 percent
of: $bedrag
```

It takes a percentage, a number declared `percentage` or a plain number, and
an amount or a number, and gives the kind of the second: 21 percent of an
amount of 10000 is an amount of 2100. The engine divides by 100, and the
operation's name says so in the YAML, which keeps RFC-023's rule that a label
never changes a value. `MULTIPLY` of an amount and a percentage stays an
error, so a hand-written product cannot silently come out a hundred times too
large. A `ratio` is refused as the percentage: a ratio of 0.21 means 21
percent, and `PERCENTAGE_OF` would read it as 0.21 percent.

The error on `MULTIPLY` protects only a number declared `percentage`. A number
that holds a percentage therefore declares the unit `percentage`, or is stored
as a `ratio`, as a definition that holds money declares `type: amount`.

The Participatiewet shows the case: it computes the reduction by hand as
`(normbedrag × verlaging_percentage) ÷ 100`, and subtracts it from the
normbedrag in a second step. With the operation, the reduction is
`PERCENTAGE_OF` the `verlaging_percentage` of the normbedrag, which reads as
the text does. Its `verlaging_percentage` is a plain `number` today, which is
the risk named under Tradeoffs.

**Dividing.** Read as dividend ÷ divisor:

| ÷ | `amount` | duration | `ratio` | `percentage` | plain |
|---|---|---|---|---|---|
| **`amount`** | plain | `amount` | `amount` | error | `amount` |
| **duration** | error | plain, the same unit only | duration | error | duration |
| **`ratio`** | error | error | plain | error | plain |
| **`percentage`** | error | error | `percentage` | plain | `percentage` |
| **plain** | error | error | plain | error | plain |

The row is the dividend, the column the divisor. `amount ÷ amount` is a plain
number: how many times the one fits in the other, or the share the one is of
the other. An output that stores it as a share declares the unit `ratio`.
`months ÷ months` is a plain number too, and `years ÷ months` an error. `amount
÷ 12` is an amount. `12 ÷ amount` would be "per eurocent", which has no type or
unit here, and is an error; today it comes out as a eurocent value.

**Rounding** (`ROUND`, `CEIL`, `FLOOR`) keeps the kind.

**Units from dates.** `AGE` gives `years`. `DATE_DIFF` gives the unit it
counts in, when `in` is written as a literal; otherwise a plain number.
`DATE_PART` and `DAY_OF_WEEK` give a plain number. The `years`, `months`,
`weeks` and `days` of `DATE_ADD` each take a plain number or a number in that
unit: `months: $termijn` with `$termijn` in `weeks` is an error.

**Where a value meets a declaration.** The rules above apply inside an
expression. Wherever a value crosses a declared field, it is checked as well:

- **Outputs.** An output of type `amount` takes an amount or a plain number,
  and an output in unit `u` takes a number in `u` or a plain number. An output
  whose value has a unit the checker knows declares that unit: `leeftijd =
  AGE …` declares `unit: years`. A value in another unit, or an amount in an
  output of type `number`, is an error; today the engine does not compare
  units here at all.
- **Inputs and parameters across laws.** An input that reads another law's
  output must agree with it: both amounts, or the same unit when both declare
  one. A parameter passed to another law follows the same rule.
- **Open terms.** The output that implements an open term has the type the
  term declares. In the new schema version an open term may declare
  `type_spec` too, and its unit is then compared as for an input; without one,
  units are not compared.
- **Overrides.** An overriding output has the type of the output it replaces,
  and the same unit where both declare one.
- **Hooks** produce ordinary outputs, so the output rule applies.
- **Callers and data sources.** A value that enters through a declared input
  or parameter is checked there for what it shows (a number, a string, a
  date) and for its `precision`. Whether a number is an amount or carries a
  unit cannot be read from the value, so it takes the kind its declaration
  gives.

**No compound units.** There is no type for "euro per day" or "per eurocent".
A rate is an `amount` with decimals: 29.43 cents per kWh is an amount of
`29.43`, and times a consumption of `2900` it gives an amount of 85347. An
amount times or divided by a duration is an amount as well: a daily amount
times `DATE_DIFF … in: days`, a yearly amount divided by a number of months.
What an amount is per is not recorded, so a monthly amount times a number of
days passes. See the open question on amounts per unit.

### Precision

Numbers are exact. No operation rounds except `ROUND`, `CEIL` and `FLOOR`, so
every rounding in a calculation is one the law prescribes (RFC-024). `1 ÷ 3`
is one third, and `(1 ÷ 3) × 3` is `1`.

Two checks keep a fraction from leaving a calculation unnoticed:

- **A declared `precision` is checked on every output**, intermediate ones
  included, and on inputs and parameters: a value with more decimals than
  declared is an error, such as `output toeslag declares precision 0 and
  received 83.33…`. The rulework then rounds where the legal text says how.
- **A finite decimal form is required where a value leaves the engine**: an
  output a caller asks for, and a value that is stored. Within a calculation,
  an output that a later step or another law reads stays an exact fraction,
  so `X ÷ 12 × 12` is `X` and nothing is rounded in between. Numbers in
  arrays and records are checked the same way, element by element, when they
  leave; a `precision` per element waits for typed records.

The first check follows DAML's rounding mode `RoundingUnnecessary`, which
refuses where another mode would round; `type_spec.precision`, metadata until
now, becomes the check.

**A limit on size.** An exact number is a fraction, and fractions with
different denominators grow when they are added: 1/3 + 1/7 + 1/11 + 1/13 is
1934/3003. Amounts divided by 12 or 365 stay small, but a `FOREACH` that
divides each element by a different number can produce a denominator of
thousands of digits, and a calculation that slows to a halt. A number whose
numerator or denominator exceeds a fixed size is therefore an error that names
the operation where it happened. The limit is a resource limit, like the
engine's limits on collection size and nesting depth, and not a rule of the
format: the implementation sets it, and raising it changes no outcome, because
the numbers stay exact. It only decides whether an answer arrives. In
practice the error points at a rulework that misses a rounding its legal text
prescribes, such as rounding each amount to whole cents before adding them,
or at a data source that delivers absurd precision.

### Errors

A combination of types that matches no row is the error
`UnsupportedOperation`, which names the operation and the operand types: `ADD
is not defined for (date, string)`. A combination of units that matches no row
is the error `UnitMismatch`, which the engine already has: `months and days
do not add`. The checker reports them as rule **T6** (types) and rule **U1**
(units), wherever it knows the types and units, and stays silent where it does
not.

Rule **U2** is a warning and refuses nothing: a ratio above `10` written in a
rulework. `just validate` prints it, as it prints its other unit warnings
today, the editor shows it, and the enrichment pipeline gets it as a finding.

T6 replaces RFC-037's rules T1 to T3, which each check part of the same
signatures. T4 (a literal assigned to an output) stays, and so does T5
(calling an article's decision), which the checker gained with RFC-045; they
are not about operations. T3 treated `date` and
`string` as one type; under T6 a `date` is a type of its own, and a string
becomes a date only through conversions 1 and 3. Both T6 and U1 run where
RFC-037's rules run, in `just validate` and when a rulework is loaded. Today
the engine checks units only when an action runs, and `just validate` checks
part of them ahead of that; U1 checks every operation at load.

What each of them can see differs. A value at run time shows whether it is a
`boolean`, a number, a `string`, a `date`, an `array` or an `object`, and the
engine refuses a wrong combination of those for every operation it executes.
It does not show whether a number is an `amount` or carries a unit, nor
whether an `object` is a `decision`: those follow from declarations, so the
checker enforces them, for every value whose declaration it knows. A branch of
an `AND` or an `IF` that is never executed is checked only by the checker.

### Extending the table

The table is closed so that additions are deliberate, not to keep it small. A
row is added in a pull request that names this RFC and adds a test for the row
in the engine, the checker and the conformance suite (`bdd/`). A row that
converts between types, rounds implicitly or introduces a type needs its own
RFC.

## Why

### Benefits

- **The format answers the question.** What `ADD` does with a date is written
  down, so a second engine is conformant or it is not.
- **Mistakes surface where they are made.** A `FOREACH` filter that returns a
  count instead of a verdict is reported, where today it filters on non-zero.
- **One table for checker and engine.** RFC-037 names "two type systems" as a
  tradeoff. Read from one table, they agree on every operation.
- **A known design.** Checking statically where a type is known and at run
  time otherwise is gradual typing (Siek and Taha, 2006).

### Tradeoffs

- **Ruleworks that run today will fail** where they rely on behavior this RFC
  ends, most likely truthiness over property paths and `IN` over a non-array
  `value`. Migration lists what the corpora meet.
- **Declared precision starts to count.** The demo corpus carries 174
  `precision` declarations in `type_spec`, most of them amounts with no
  decimals; `corpus/regulation` and `corpus-poc` carry none. An output that
  now receives an unrounded value behind such a declaration fails until the
  rulework rounds it where its legal text prescribes, or drops the
  declaration.
- **Strictness costs convenience.** `IN 5 ["5", 6]` was a harmless `false`;
  now the author has to make the list consistent.
- **A percentage is checked only when it is declared.** A whole percentage
  stored as a plain number (`21`) passes `MULTIPLY` with an amount and gives a
  result a hundred times too large. This is the argument this RFC uses against
  money as a unit, and it holds here too: no field in the corpus declares
  `percentage` today. The fields named after a percentage mostly store a
  `ratio` (`0.01896`) and are safe; the risk is a whole percent left plain.
- **Values without a declaration are checked only for what they show.** A field
  of a record (`$kind.toeslag`), a `FOREACH` element and an array item have no
  declared kind, so `amount`, units and `decision` are not checked for them:
  `$kind.toeslag × $regeling.percentage` passes as two numbers. In the corpus
  that is about 4 percent of the operands of arithmetic; the other 96 percent
  are declared fields, definitions and outputs.

### Alternatives Considered

**Adopt FEEL.** FEEL (DMN) has the most complete operator tables of the
surveyed systems and a Rust implementation (`dsntk`). It has no money or units,
and its `null` flows through arithmetic, which RFC-036 forbids for an absence.
RFC-011 already chose against DMN as the rules language.

**Adopt CQL's quantities.** HL7 CQL, a language for clinical rules, has
quantities with UCUM units, calendar durations and three-valued logic. It has
no money, and an operation that fails returns `null` where this format raises
an error.

**Adopt Catala's types.** Catala's money and date rules are the closest to what
a law needs. It rounds money to the cent automatically, where RFC-024 rounds
only where the law says so, and it keeps whole and decimal numbers apart, where
the corpus treats them as one `number`. There is no Rust runtime.

**A fixed working precision.** IEEE 754 decimal128 fixes 34 digits and
rounds ties to even, and FEEL means its numbers to behave that way. It would
make the format, not the library, decide the last digit, and it keeps numbers
bounded. It is still a rounding the law did not prescribe, and `FLOOR` after a
division can still land on the wrong side of a whole number. Catala, a
language for law, uses exact fractions for the same reason. A fixed number of
decimals per field, as SQL's `DECIMAL` does, needs a rule per operation for the
decimals of the result, and SQL itself leaves that rule for division to each
database.

**Money as a unit on `number`.** Money could be `number` with the unit
`eurocent`, with `amount` removed, which puts every quantity in one model.
Units are optional, though, and a money field without its unit would drop out
of every money rule; 94 of the 656 `amount` fields that can declare a unit
declare none today. A type is required on every field, so `amount` is always
checked.

**Document today's behavior.** That makes the engine predictable without
breaking a rulework, but it puts "a non-empty string is true" into the law
format, which no legal text means.

**Complete the checker and leave the engine alone.** The checker cannot see
property paths, `FOREACH` bindings or array elements, and values also reach the
engine from callers and data sources. The engine has to refuse what a value
shows by itself.

## Implementation Notes

- **One table.** The signatures and the unit rules live in one module of the
  engine crate, read by `typecheck.rs` for T6 and U1 and by `operations.rs`
  before each operation. A reference page in the docs is rendered from it.
- **A date value.** To refuse `ADD` of a date and a string at run time, the
  engine must tell a date from a string. `Value` gains a `Date` variant, parsed
  at the boundary and written back as `YYYY-MM-DD`, so traces, the WASM API and
  stored values keep their form.
- **Money as a type.** A new schema version drops `euro` and `eurocent` from
  the unit list; released versions keep them, because they are frozen. From
  an older version, `eurocent` on an `amount` is accepted and ignored,
  `eurocent` on a `number` is read as an `amount`, and `euro` is refused with
  a message that names the fix: an `amount`, the value times 100. No
  rulework in the corpus uses `euro` or `eurocent` on a `number`. The
  frontends decide on `type: amount` alone; the editor today also requires the
  unit and enters a unit-less amount as is, where the demo shows it as euros.
- **`PERCENTAGE_OF`** is a new operation in the same schema version, with a
  row in the arithmetic table, a unit rule and a conformance scenario like
  every other. Its trace step shows the percentage, the amount and the
  result.
- **Exact numbers.** `rust_decimal` gives way to an arbitrary-precision
  rational type (`num-rational` or `malachite`). Values that leave the engine
  are still written as decimals, since the second check guarantees they have a
  finite form. A trace shows an intermediate value without one as a fraction,
  such as `1/3`.

## Migration

This RFC changes rules under which today's ruleworks are correct, so
implementing it includes bringing the corpora along. It lands as schema
v0.9.0, a breaking version after v0.8.16: it removes the units `euro` and
`eurocent`, and adds `PERCENTAGE_OF` and `type_spec` on open terms. Released
versions stay as they are, and the engine reads them as Implementation Notes
describes.

What the corpora meet, counted in November 2026:

| Change | `regulation` | `demo` | `corpus-poc` | How |
|---|---|---|---|---|
| `unit: eurocent` on an amount, dropped | 56 | 124 | 382 | script |
| additions that mix an amount with money in a definition without `type: amount` | 2 | 46 | 0 | by hand: the definition gets `type: amount` |
| outputs whose value has a known unit but declare none | 6 | 1 | 6 | script, the unit follows from `AGE` or `DATE_DIFF` |
| outputs ending in a division without rounding | 3 | 12 | 29 | by hand: 10 declare a `precision`; the rest fail only if the value leaves the engine without a finite form |
| `MAX` or `MIN` with the literal `0` | 2 | 21 | 38 | none, allowed by the rule for zero |
| truthiness, `IN` over a non-array, `EQUALS` across types | | | | counted by step 1, fixed by hand |

`corpus-poc` is outside `just validate`, but its proofs of concept run on the
engine, so it moves along.

1. Implement T6, U1 and the precision checks in a mode that reports instead
   of refusing, and run it over all three corpora.
2. Apply the script for the mechanical rows. Fix every other finding in the
   rulework, or add the row the law turns out to need.
3. Switch from reporting to refusing in the change that lands the fixes and
   schema v0.9.0.

RFC-037's zero-findings test stays and covers T6 and U1; because the fixes
land with the switch, it stays green. RFC-037 narrows a rule that fires on a
correct rulework, because such a finding is a bug in the checker. Here the
rules themselves change by decision of this RFC, so what counts as a correct
rulework changes with them, and the corpus moves instead of the rule.

## Open Questions

- **Conversion between units.** Apart from `PERCENTAGE_OF`, the rules leave
  no way to turn a `percentage` into a `ratio`, or `years` into
  `months`: multiplying by a plain `100` or `12` keeps the original unit, and
  the output then refuses it. Options: a conversion operation for the exact
  factors (`percentage` to `ratio`, `years` to `months`, `weeks` to `days`),
  or declaring every value in its target unit from the start.
- **Other currencies.** A rulework from a country outside the euro, or a
  Dutch version from before 2002 in guilders (the demo corpus has a Wet
  inkomstenbelasting dated 2001-01-01), needs a currency other than the euro.
  The currency would belong to the rulework version, since a law counts in
  one currency and that currency can change over time, with the minor unit
  taken from ISO 4217: two decimals for the euro, none for the yen, three for
  the Kuwaiti dinar. Amounts in different currencies never combine, and an
  input that reads an amount in another currency is an error, as a unit
  mismatch is. Conversion is an explicit step at a rate the law or regulation
  gives, never implicit.
- **Fractions and percentages as types.** Money is a type because a type is
  required and a unit is not. The same argument would make `percentage`, and
  then `ratio`, types of their own, leaving units only for durations. That
  closes the gap named under Tradeoffs, at the cost of reworking what units
  are; how often enriched ruleworks hold whole percentages should decide it.
- **Amounts per unit.** A rate modeled as a plain `amount` loses what it is
  per: a price per kWh can be added to a total, a price per MWh taken for one
  per kWh, and a monthly amount multiplied by a number of days. An `amount`
  with `type_spec.per` (`per: kWh`, `per: days`) would keep it, with rows such
  as amount per `u` × number in `u` gives an `amount`, and amount ÷ number in
  `u` gives an amount per `u`. Measured
  quantities (kWh, m³, GJ, liters, kilograms) would need units of their own,
  for which UCUM has standard codes. Such calculations come from enriching
  regulations such as energy tariffs and excise duties, and are rare in the
  corpus, so the plain-amount rule above is enough until one needs more.
- **Dates in `MIN` and `MAX`.** "The later of two dates" is a common legal
  construction; it is left out until a law needs it.
- **A non-array `FOREACH` collection.** Iterating it once hides a data source
  that delivered one record where the rulework declares a list. Making it an
  error moves that fix to the data source.

Out of scope, each for a separate RFC: typed records and arrays, which would
let the checker see the fields of an `object` and the items of an `array`, and
a data source or caller be checked against them where a record comes in; and
an option for `DATE_ADD` to refuse a day past the end of the month.

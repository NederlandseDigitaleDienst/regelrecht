## Context

Dossier corpora are increasingly written outside the editor. Someone, often an agent, works in a local clone of a private corpus repo, on a working branch, and pushes. The editor should show that work and allow edits on it, without either side breaking the other.

The editor already commits: every save is one Contents API commit on the traject branch `traject/<slug>-<8hex>`, cut from the traject's `base_branch`. For git the editor is just another committer. Four things still went wrong when a clone and the editor shared a repo:

1. **A shared branch tip.** The editor checks the blob sha per file (one retry, then 409), but there is no compare-and-set on the branch tip, and a save spanning several files is not atomic. Two writers on one branch get 409s on one side and non-fast-forward pushes on the other.
2. **Whole-file rewrites.** The editor saved by `yaml.dump`-ing the reassembled document. That drops every `#` comment, refolds lines at 80 columns and can reorder keys. Hand- and agent-written corpora carry many comments (one dossier corpus has them in 12 of its 17 rulework versions), so every save became a whole-file diff and the next merge with the clone conflicted.
3. **Drift.** The working branch keeps moving after the traject is created. Nothing brought the traject up to date, and nothing described the way back.
4. **Loading.** A repo that is also in the local registry as a `local` source sat at the same priority (0) as the traject's own source. Equal priority on one `$id` is a hard `SourceMap` error, so the traject index did not build at all. Notes sidecars at the repo root are invisible when the source root is a sub-path, and a version that will not load only showed up as a failed save.

## Decision

**Two branches, merges in both directions, never a shared tip.** The working branch belongs to the clone; the editor never writes to it. The traject branch belongs to the editor. Each side only ever fast-forwards its own branch.

- *Working branch to traject:* `POST /api/trajects/{ref}/sync-base` fast-forwards the traject branch when it has no commits of its own, and otherwise merges the working branch into it through the GitHub Merges API. A conflict (409) leaves both branches untouched; the response then names the files changed on both sides and the `git merge` to run in the clone. The handler holds the writable source's backend lock from the divergence check through the ref update, and invalidates the traject snapshot afterwards. The fast-forward matters: the Merges API always writes a merge commit, which would otherwise count as traject work the working branch lacks.
- *Traject to working branch:* `POST /api/trajects/{ref}/propose` opens or refreshes a pull request from the traject branch to the working branch. In the clone, `git merge origin/traject/<slug>` does the same.
- *Automatically:* while a traject is open, the editor checks every three minutes, and when the tab becomes visible again. When the working branch changed files the traject lacks, it runs the same sync (`?auto=true`). The GitHub merge is git's three-way merge, so changes to different lines of one file merge without help. A real conflict, the same lines changed on both sides, is not retried until either branch moves. Git cannot settle that without discarding one side, so the editor leaves it to a person, who resolves it in the clone. After a sync the editor drops its cached law bodies and reloads the open article unless it has unsaved edits; those are kept, and the save's `If-Match` reports the changed file. With `auto`, a missing GitHub link answers 409 rather than 428, so the loop never opens the connect flow.
- `GET /api/trajects/{ref}/base-status` reports `behind_by`, `ahead_by` and the files changed on each side. The library view shows a banner when either side changed files the other lacks. It counts files, not commits, so a merge commit alone does not bring it back. It stays silent on the central corpus, and when the user has no GitHub link the endpoint answers 409 instead of starting the connect flow.

**Saving preserves the file.** The editor splices instead of re-dumping (`frontend/src/lib/yamlPatch.js`). It parses the stored text with the comment-aware `yaml` library, locates the source range of the changed field, and replaces only those bytes. Inside `machine_readable` it descends to the smallest changed subtree, so comments next to unchanged definitions survive an edit elsewhere in the same article. Only when the document has a shape the patcher does not handle does it fall back to the old full re-dump.

**The traject's own source always wins.** When the index is built, every seed source is shifted by the same amount until it sits strictly below the writable source (`effective_priorities` in `traject_corpus.rs`). The seeds keep their order among themselves, and existing trajects benefit without a migration.

**Loading starts with a preflight.** `POST /api/trajects/preflight` reads a repo without creating anything. It reports the branches, the rulework versions under the source root, which of them fail the engine's load contract (YAML, a top-level `$id`, deserialization into the law model), which `$id`s other sources also serve, and whether notes sit at the repo root while the editor looks under the source root. The create form uses it to fill the working-branch picker and blocks creation on a blocker finding.

## Why

### Benefits

- Neither side can rewrite the other's history, and every conflict surfaces as an ordinary git merge conflict, in a place where the tools to resolve it exist.
- An editor save on one article now changes one or two lines. Measured on two corpora (246 articles with `machine_readable`), changing one leaf or adding one key never touched more than two lines and lost no comment; the previous path rewrote the file.
- No new storage, no locks across processes, no clone on the server. The Merges API does the merge.

### Tradeoffs

- Edits reach the working branch only through a merge. Someone has to press "Bijwerken" or merge the pull request; the editor does not do it on its own.
- The preflight checks the engine's load contract, not the full JSON schema. A version that passes can still have findings from `just validate`.
- The YAML patch handles block maps and sequences of equal length in place. A changed sequence length or a flow collection re-renders that one pair, which drops comments inside it.

### Alternatives Considered

**Editor and clone on the same branch.** Live, but both writers race for the tip: the clone needs `pull --rebase` before every push and the editor turns those races into 409s for its users.

**Editor writes into the local working tree.** No commits from the editor, no remote round trip. Only works on one machine, and it bypasses the attribution and access checks that the traject flow carries.

**Full JSON-Schema validation in the preflight.** Needs `jsonschema` in the editor API and fetching the schema version per file. Deferred; the load contract catches what makes a rulework fail to open.
